# pain001-loader-xlsx v0.0.65

No loader changes: `XlsxLoader` behaves exactly as it did in 0.0.63.
What this release adds is a benchmark that measures the one thing
separating its two entry points, plus the suite tooling this repository
was missing — and it removes a tag that should never have existed.

## Why the number jumped from 0.0.63

The `pain001` suite ships **one version number across all five
packages** by policy, and it had drifted to four: 0.0.62, 0.0.64,
0.0.63, 0.0.62 and 0.0.63.

Nothing breaks when that happens, which is exactly the problem. A member
left a release behind still installs, still imports, and still passes its
own tests. Only the index disagrees, and only if somebody looks.

All five now sit on **0.0.65**.

## The benchmark

`load` returns every row at once. `load_streaming` yields fixed-size
chunks. Time is near-identical — openpyxl's parsing dominates both — so
the only question worth measuring is peak memory.

| rows | eager MB | streamed MB | materialised MB |
| ---: | ---: | ---: | ---: |
| 500 | 0.85 | 0.77 | 0.85 |
| 2,000 | 2.02 | 1.30 | 2.02 |
| 10,000 | 8.73 | **1.96** | 8.73 |

At 10,000 rows, streaming and releasing each chunk peaks **4.5× lower**
and stays roughly flat as the file grows.

### The third column is a mistake, kept on purpose

`materialised` is `list(loader.load_streaming(path, 500))` — streamed and
then kept. It costs **exactly** what `load()` costs, because it retains
every chunk, which is the one thing streaming exists to avoid.

It is in the table because the first version of this benchmark measured
the streaming path that way and reported that streaming saves nothing —
a wrong number that looked plausible enough to be quoted. Callers make
the same mistake in real code.

**The saving comes from consuming a chunk and letting it go**, not from
calling `load_streaming` instead of `load`.

One stated limit: peak comes from `tracemalloc`, which sees Python-level
allocations only. openpyxl's C-level XML parsing is not counted, so read
these as a floor and as a comparison between the three paths — not as a
budget.

## Removed: the stray `v0.1.0` tag

`v0.1.0` was pushed in error on 2026-08-20, against a tree that briefly
declared `0.1.0`. It was never released to PyPI, had no GitHub release,
and contradicted this suite's numbering, where `0.1.0` follows `0.0.999`.
The version line it interrupted continued correctly at `0.0.61`.

The tag is deleted. Nothing depended on it.
