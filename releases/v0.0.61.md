# pain001-loader-xlsx Release v0.0.61

**Release Date:** 2026-08-20
**Tag:** v0.0.61
**Python:** 3.10+
**Status:** Stable

## Executive Summary

> **0.0.60 was never published.** It was prepared and tagged, but the tag
> failed before the publish step, and by the time that was corrected the
> suite had moved to 0.0.61. This release carries 0.0.60's contents
> unchanged, plus the suite version bump.


Two things: a correctness fix in how cell values reach `pain001`, and the
end of a version number that claimed something untrue.

**Values are now text, and date cells are refused.** openpyxl hands back
native Python objects — `float` for numerics, `datetime` for anything
Excel considers temporal. Those were passed straight through, so a
payment amount arrived as `100.0` rather than `"100.00"`, and a
`datetime` arrived where an ISO date string was expected. Values are now
normalised to text with the cell's own number format taken into account,
and temporal cells are rejected with a message naming the offending cell
rather than silently producing a document that fails schema validation
later.

**The version is `0.0.60`, matching the rest of the suite.** The
previous release was `0.0.54` while requiring `pain001 >= 0.0.56` — a
version claiming to belong to a release line it predates. The CHANGELOG
stated the rule ("a `0.0.X` release of this package targets the `0.0.X`
release of `pain001`") and the metadata contradicted it.

The fix is to honour the rule rather than abandon it. Every package in
the suite ships the same version number, so `pain001-loader-xlsx
0.0.60` pairs with `pain001 0.0.60` and there is no table to consult.
Versions advance in `0.0.1` steps along the `0.0.x` line; `0.1.0`
follows `0.0.999`.

## What's in v0.0.61 at a glance

- **Cell values are normalised to text** using the cell's number format,
  so amounts keep their trailing zeros and integers do not arrive as
  floats.
- **Temporal cells are refused** with the cell reference in the error,
  instead of passing a `datetime` into a field that expects a string.
- **Version aligned to the suite.** `0.0.54` -> `0.0.60`, matching
  `pain001`, `pain001-mcp`, `pain001-lsp` and `pain001-loader-mt101`.
  See `pain001.suite`, which a daily job checks against PyPI.
- **Benchmarks with real guards.** A measurement plus two guards: one
  comparing load time against itself at two sizes (machine-independent,
  so it does not flake on shared runners), and one asserting that
  `load_streaming` peaks well under a full load. The second exists
  because the way streaming breaks is not a slowdown — it is someone
  re-implementing it as a full load plus slicing, which keeps every row
  correct and every timing identical. Only peak allocation separates
  them: 885 KiB streaming against 3628 KiB for a full load.

## Compatibility

`pain001 >= 0.0.56, < 1` is unchanged. Nothing in this release requires
a newer core.

The value change is breaking for any caller that relied on receiving
native Python objects from this loader. Callers feeding rows into
`pain001` are unaffected — text is what it expected all along.
